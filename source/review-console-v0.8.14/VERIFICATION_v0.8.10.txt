Live browser test (isolated localhost:8779 session, real keystrokes)
The v0.8.9 handoff recorded that segment-by-segment typing had never been reproduced by actually
typing. That gap is closed for the typed-time path. Every step below used real key events unless
stated otherwise.

1. Typed "20" into START. The box held "20" with the caret still at position 2 in the same box.
   It did not become "2" and it did not jump to minutes. This is the exact reported failure.
2. The box was marked incomplete and the note read "Start time is incomplete - finish the entry.
   Anything already saved is kept until a complete value is entered."
3. Continued typing "00" gave "2000"; the mark and note cleared. Tab settled the box to "20:00".
4. Typed "2100" into END and tabbed out: START 20:00, END 21:00, HRS 1.
5. Added the secondary. Stored startTime 20:00, endTime 21:00, totalHours 1.
6. Reopened it, selected the END contents and typed "20" over the saved 21:00. The box went red
   with the End time note, and the stored endTime remained 21:00. An unfinished typed time did
   not delete the saved one.
7. Completed END to "2200": stored endTime 22:00, totalHours 2.
8. Deliberately cleared END: the endTime key was removed from the record, startTime was
   untouched, and the box was not marked incomplete. Deliberate clearing still works.
9. Restored END to 21:00, waited for the footer to confirm "Auto-saved on this device", then
   performed a full page reload. Stored values survived: 20:00 / 21:00 / 1.
10. Inline activity composer: typed "2230" into START and "23" into END. START settled to 22:30;
    END showed the incomplete mark and note. Completing to "2345" cleared the warning and
    calculated HRS 1.25. Add Activity stored the activity at 22:30 / 23:45 / 1.25 with zero
    children, and the parent secondary's own times were untouched.
11. iPhone viewport (375x812, touch emulation): the boxes render as type="text" with
    inputmode="numeric" and maxlength="5", so iOS shows the numeric keypad. START, END and HRS
    still fit one row; WORK DATE keeps its native date control.
12. No console errors at any point.

Test-harness limits, stated plainly
- The browser pane in this session could not deliver Backspace or Delete to an input. Character
  keys, Tab, End and clicks all worked; deletion keys left the value unchanged with the caret in
  the right place. Step 8 above was therefore driven by setting the value and dispatching the
  same input and focusout events the keyboard produces, which exercises the real handlers and the
  real commit path but is not an OS-level keypress. Every other step used genuine keystrokes.
- One earlier reload check appeared to lose an edit. That run was invalid: the reload was issued
  in the same batch as the edit and raced the asynchronous save. Repeated with a wait for the
  auto-save confirmation, the values persisted correctly (step 9).
